# 中国航发动力所工业图像智能算法工具统一API 接入规范

## 1. 目的与适用范围

本规范用于工业图像智能算法工具的服务封装、接口调用、输入输出、运行环境、CPU硬件要求、性能测试、日志、交付及验收要求。目标是使上层AI智能体或统一调度平台能够以一致方式发现、调用和解释各专业算法工具。

算法模型内部实现方式不作统一限制，但对外服务行为必须满足本规范或经批准的偏离项。

## 2. 总体设计原则

| 原则 | 要求 |
|------|------|
| **统一外部接口** | 不同开发单位的内部模型结构可以不同，但服务入口、公共字段、错误码语义和版本信息应尽量统一。 |
| **结构化结果优先** | 算法工具首先输出机器可读JSON，供AI智能体继续推理；人可读报告或标注图作为可选产物，不应替代结构化结果。 |
| **CPU可部署** | 当前基线为CPU推理。开发方必须声明CPU架构、指令集、线程模型、内存和性能要求，不得存在未申报的GPU/CUDA依赖。 |
| **环境可复现** | 所有Python包和系统依赖应版本锁定，禁止依赖开发机中未声明的隐式环境。 |
| **可观测可诊断** | 服务应提供健康检查、运行日志、统一错误返回和关键耗时信息，便于平台侧诊断。 |
| **版本可追溯** | 工具版本、模型版本和接口版本必须可区分，输出结果应能追溯到实际运行版本。 |

## 3. 参考系统架构

```
AI智能体 / 统一调度平台
│
├── POST /api/v1/inference → 孔探检测服务
├── POST /api/v1/inference → 断口分析服务
├── POST /api/v1/inference → 热端部件缺陷检测服务
├── POST /api/v1/inference → 其他算法服务
│
└── 接收统一JSON结构结果 → 智能体融合分析 → 综合报告
```

原则上，每个算法工具独立封装为可部署服务。上层AI智能体不直接导入各开发方Python模块，不依赖各开发方内部目录结构或私有调用函数。

## 4. 统一技术基线

| 项目 | 统一要求 |
|------|----------|
| 服务形式 | REST API |
| 通信协议 | HTTP；生产环境可由平台统一配置HTTPS |
| 请求/响应字符编码 | UTF-8 |
| 结构化响应 | application/json |
| 图像上传 | multipart/form-data |
| 接口版本 | /api/v1/... |
| 推理硬件 | CPU-only 基线 |
| GPU/CUDA依赖 | 基线不允许；确需时必须单独申报并批准 |
| Python版本 | 开发方固定到具体版本，如3.9.x |
| 模型权重 | 本地可加载，路径可配置 |
| 外网依赖 | 运行时原则上不得依赖公网下载模型或数据 |

## 5. 服务接口规范

### 5.1 健康检查接口

`GET /health`

```json
{
  "code": 0,
  "message": "success",
  "status": "healthy",
  "tool_name": "borescope_defect_detection",
  "tool_version": "1.0.0",
  "model_version": "1.0.0"
}
```

- 健康检查不得执行完整推理任务，应在较短时间内返回。
- 如模型需要预加载，开发方应说明health仅检查进程存活，还是同时检查模型可用状态。

### 5.2 推理接口

`POST /api/v1/inference`  
`Content-Type: multipart/form-data`

| 字段 | 类型 | 必填 | 统一性 | 说明 |
|------|------|------|--------|------|
| image | File | 是* | 统一字段 | 单图工具使用；多图工具可使用images并在填报表说明 |
| task_id | String | 是 | 统一字段 | 调用方生成的任务唯一编号，原样返回 |
| parameters | JSON String | 否 | 统一字段 | 算法特有可调参数；必须给出默认值和取值范围 |
| engine_id | String | 否 | 公共扩展 | 发动机编号 |
| component_id | String | 否 | 公共扩展 | 部件编号/部位编号 |
| image_id | String | 否 | 公共扩展 | 图像业务编号 |
| trace_id | String | 否 | 公共扩展 | 链路追踪编号；如未提供可由服务生成 |

> *多图、图像+元数据、成组图像等特殊输入形式允许扩展，但必须在配套Excel中完整列出，并提供可执行请求样例。

### 5.3 请求参数原则

- 参数名称使用小写英文与下划线，例如 `confidence_threshold`。
- 不得要求AI智能体了解模型内部张量名称、Python对象或本地绝对路径。
- 算法参数应提供默认值；非必要参数不得设置为必填。
- 阈值类参数须明确单位、范围、默认值和越界处理方式。

## 6. 图像输入规范

| 项目 | 必须填写内容 | 示例 |
|------|--------------|------|
| 支持格式 | JPEG/JPG、PNG、TIFF等 | JPG、PNG、TIFF |
| 色彩模式 | RGB、BGR、灰度、16bit等 | RGB/Gray |
| 最小分辨率 | 宽×高像素 | 512×512 |
| 推荐分辨率 | 典型生产输入 | 2048×2048 |
| 最大分辨率 | 超过后的行为必须说明 | 8192×8192 |
| 最大文件大小 | MB | 50 MB |
| 多图输入 | 是否支持、最大张数、顺序语义 | 支持，2~20张 |
| 预处理 | Resize/Crop/Normalize/去噪等完整流程 | 保持长宽比缩放至1024 |
| EXIF方向 | 是否自动校正 | 是 |
| 异常图像处理 | 损坏、空文件、通道不符等 | 返回统一输入错误码 |

## 7. 统一响应结构

所有推理接口应返回统一"外壳"结构。算法特有结果放入 `result` 对象中；不得将成功时返回JSON、失败时返回纯文本或HTML错误页。

```json
{
  "code": 0,
  "message": "success",
  "task_id": "TASK202608140001",
  "trace_id": "TRACE-001",
  "tool": {
    "tool_name": "borescope_defect_detection",
    "tool_version": "1.0.0",
    "model_version": "2.1.0",
    "api_version": "v1"
  },
  "input": {
    "image_name": "001.jpg",
    "width": 2048,
    "height": 2048
  },
  "performance": {
    "processing_time_ms": 3260
  },
  "result": {
    "status": "abnormal",
    "summary": "检测到1处疑似裂纹缺陷",
    "defects": [
      {
        "defect_id": "D001",
        "defect_type": "crack",
        "defect_name_cn": "裂纹",
        "confidence": 0.932,
        "severity": "medium",
        "location": {"type": "bbox", "bbox": [120, 230, 460, 580]},
        "description": "叶片区域存在疑似裂纹"
      }
    ]
  },
  "artifacts": []
}
```

| 一级字段 | 必填 | 说明 |
|----------|------|------|
| code | 是 | 业务状态码；0表示成功 |
| message | 是 | 简要状态说明 |
| task_id | 是 | 与请求一致 |
| trace_id | 建议 | 便于日志追踪 |
| tool | 是 | 工具、模型和API版本信息 |
| input | 是 | 实际处理输入的关键元信息 |
| performance | 是 | 至少包含本次处理总耗时 |
| result | 是 | 算法结构化结果 |
| artifacts | 否 | 标注图、单工具报告等衍生产物信息 |

### 7.1 result 字段设计原则

- 检测类工具建议返回 `defects` 数组；分类/判定类工具可返回 `label`、`score`、`conclusion` 等字段。
- 缺陷类别应同时给出稳定英文编码和中文名称，避免仅输出自然语言。
- 置信度统一建议使用0~1浮点数；如算法不具备概率意义，应明确 `score` 的统计含义。
- 位置字段应明确坐标系。`bbox` 建议定义为 `[x_min, y_min, x_max, y_max]`，原点位于原始图像左上角，单位为像素。
- 分割结果可使用 `polygon`、`mask` artifact 或其他明确定义的方式，不建议将大尺寸mask直接嵌入主JSON。
- 算法无法给出严重度时，不得伪造 `severity`，可返回 `null` 并在字段说明中标明"不支持"。

### 7.2 报告与衍生产物

建议专业算法服务输出结构化结果，由AI智能体统一生成最终综合报告。若算法工具自身必须生成标注图、HTML/PDF/Word或专业分析报告，应通过 `artifacts` 返回产物元信息，而不是仅返回一个不可解析的报告文件。

```json
"artifacts": [
  {
    "artifact_type": "annotated_image",
    "mime_type": "image/png",
    "name": "001_annotated.png",
    "uri": "/artifacts/TASK202608140001/001_annotated.png"
  }
]
```

## 8. 错误码与异常处理

| 业务码 | HTTP状态 | 名称 | 说明 |
|--------|----------|------|------|
| 0 | 200 | SUCCESS | 处理成功 |
| 1001 | 400 | INVALID_REQUEST | 缺少必填字段或参数格式错误 |
| 1002 | 415 | UNSUPPORTED_IMAGE_FORMAT | 不支持的图像格式/通道 |
| 1003 | 413 | IMAGE_TOO_LARGE | 文件大小或分辨率超过限制 |
| 1004 | 422 | INVALID_IMAGE | 图像损坏、无法解码或内容无效 |
| 2001 | 422 | INVALID_PARAMETER | 算法参数越界或组合不合法 |
| 3001 | 503 | MODEL_NOT_READY | 模型未加载或初始化失败 |
| 3002 | 500 | INFERENCE_FAILED | 模型推理执行失败 |
| 3003 | 504 | INFERENCE_TIMEOUT | 推理超过服务超时 |
| 4001 | 500 | INTERNAL_ERROR | 未分类内部错误 |

```json
{
  "code": 1002,
  "message": "unsupported image format: bmp",
  "task_id": "TASK202608140001",
  "trace_id": "TRACE-001",
  "result": null
}
```

## 9. 软件环境与依赖要求

| 类别 | 开发方必须说明 |
|------|----------------|
| 操作系统 | 开发/验证OS名称、版本、内核或发行版；生产推荐环境 |
| Python | 精确版本；是否支持其他小版本 |
| Python依赖 | requirements.txt / lock文件；包名与固定版本 |
| 系统依赖 | OpenCV系统库、libGL、gcc runtime、OpenMP等 |
| 推理框架 | PyTorch、ONNX Runtime、TensorFlow等及版本 |
| 数值库 | NumPy、MKL/OpenBLAS等及版本或依赖关系 |
| 模型文件 | 文件名、大小、校验值（建议SHA256）、加载方式 |
| 配置文件 | 配置项名称、默认值、环境变量或配置文件路径 |
| 启动方式 | 一条可复现启动命令 |
| 网络依赖 | 运行时是否访问公网、数据库、文件服务等 |
| 许可证 | 第三方依赖或模型使用限制（如有） |

要求：开发方不得仅提交"pip freeze"而不说明关键依赖用途。对于PyTorch、ONNX Runtime、OpenCV、NumPy等关键库必须单独列示。

## 10. CPU硬件与资源要求

所有工具当前按CPU推理基线接入。开发方应提供可量化、可复现的硬件条件，禁止使用"i7以上""高性能CPU""16G以上即可"等无法用于部署设计的模糊描述。

| 项目 | 必须填写 | 说明/示例 |
|------|----------|-----------|
| CPU架构 | 是 | x86_64 / ARM64 |
| 实际测试CPU型号 | 是 | 如 Intel Xeon Gold xxxx |
| 最低物理核心数 | 是 | 如 4 Core |
| 推荐物理核心数 | 是 | 如 8 Core |
| CPU指令集依赖 | 是 | SSE4.2 / AVX / AVX2 / AVX512 / 无特殊要求 |
| 线程配置 | 是 | 推理线程数、OpenMP/MKL线程；是否可配置 |
| 最低内存 | 是 | 如 8 GB |
| 推荐内存 | 是 | 如 16 GB |
| 模型加载常驻内存 | 是 | 如 2.3 GB |
| 单任务峰值内存 | 是 | 如 4.6 GB |
| 磁盘空间 | 是 | 代码+环境+模型+临时文件 |
| 临时空间 | 是 | 单任务最大临时磁盘占用 |
| 并发建议 | 是 | 单实例建议并发及限制 |
| NUMA/绑核要求 | 如有 | 多路CPU服务器如有特殊要求需声明 |

## 11. 性能测试与基准要求

各单位性能指标必须附带测试环境和测试图像规格，否则耗时数据不具可比性。建议牵头单位提供一组统一基准图像，同时保留各算法自身典型数据集测试。

| 测试项 | 统一记录要求 |
|--------|--------------|
| 测试机器 | CPU完整型号、物理核/逻辑核、内存、OS、Python、推理框架版本 |
| 图像规格 | 数量、格式、分辨率分布、平均文件大小 |
| 模型预热 | 至少记录是否预热及预热次数；建议前5次不计入正式统计 |
| 单任务延迟 | Avg、P50、P95、Max，单位ms或s |
| 模型初始化 | 服务启动到可接受推理请求的时间 |
| 内存 | 模型加载后常驻内存、推理峰值内存 |
| CPU利用率 | 测试期间平均/峰值CPU使用情况，可选 |
| 并发 | 并发1/2/4或开发方建议值下的吞吐与延迟 |
| 吞吐 | images/s 或 tasks/min |
| 连续稳定性 | 建议连续处理≥100个样本，记录失败数和异常 |

## 12. 日志与可观测性

- 日志至少包含：时间、日志级别、tool_name、task_id/trace_id、接口、处理耗时、结果状态和异常摘要。
- 默认日志不得记录完整原始图像内容或Base64。文件名、发动机编号等业务信息是否记录应支持配置。
- 异常日志应保留可定位的错误信息，开发模式可记录堆栈；生产模式不得直接将完整堆栈返回给调用方。
- 应说明日志路径、滚动策略、单文件大小、保留周期和磁盘上限。

## 13. 部署与运行要求

1. 必须提供从干净环境开始的部署步骤。
2. 必须提供一条启动命令，明确监听地址、端口、工作进程/线程参数。
3. 模型路径、端口、日志目录、线程数等部署项应通过配置文件或环境变量控制，不得硬编码为开发机路径。
4. 服务启动后应先完成必要的模型加载，并通过 `/health` 暴露可用状态。
5. 服务退出应能正常释放文件句柄、临时文件和线程资源。
6. 运行时原则上不得自动联网下载模型、字体、权重或其他依赖。

## 14. 安全与数据处理基本要求

- 不得在代码中硬编码账号、口令、Token或私有服务地址。
- 对于本地文件访问应限制在配置的工作目录内，避免接受任意绝对路径作为推理输入。
- 如服务需要鉴权，由牵头单位平台统一设计；算法服务应预留兼容能力。

## 16. 验收要求

| 验收类别 | 验收点 | 判定要求 |
|----------|--------|----------|
| 启动 | 干净环境可部署 | 按文档可完成安装/镜像启动，不依赖开发者手工补文件 |
| 健康检查 | /health | 服务可用时返回200及标准JSON |
| 接口 | 推理调用 | 标准样例请求可成功，字段符合填报说明 |
| 输入 | 格式边界 | 合法输入成功；不合法输入返回明确错误码 |
| 输出 | 结构化结果 | 关键检测结果不能只藏在自然语言报告中 |
| 版本 | 可追溯 | 返回tool/model/api版本 |
| CPU | 无隐式GPU依赖 | 无CUDA/GPU才能启动或推理的隐藏依赖 |
| 资源 | 内存/CPU | 不超过申报峰值的合理误差范围 |
| 性能 | 基准测试 | 达到开发方申报值或项目约定阈值 |
| 并发 | 稳定性 | 在申报并发下无明显崩溃、串结果或资源泄漏 |
| 异常 | 错误处理 | 服务不因单个错误图像整体退出 |
| 日志 | 可追踪 | 可通过task_id/trace_id定位请求 |
| 连续运行 | 稳定性 | 批量连续任务无异常退出；失败可追踪 |
| 交付 | 材料完整 | 第15章交付物齐全 |

## 17. 版本与变更管理

- 接口路径中的 `v1` 表示接口大版本。破坏兼容性的字段删除、语义修改或输入方式变化应升级大版本。
- 模型权重变化应修改 `model_version`，即使API不变。
- 服务代码修复应修改 `tool_version`。
- 任何已上线字段原则上不得静默改变单位、坐标系、枚举值或置信度含义。
- 开发方提交新版本时需提供变更说明、回归样例及对历史调用兼容性的说明。

| 类别 | 建议字段 |

| 图像证据 | 原图引用、标注图引用、局部裁剪图（如适用） |
