- **致**：拟在 15.106 上部署的各项目团队（工业图像智能体、多学科仿真智能体、数字发动机建模智能体）
- **发起单位**：工业图像智能体项目组（quality-agent / vision-agent，已先行部署）
- **目标主机**：192.168.15.106（中科方德高可信服务器 OS 4.0 RTM4，128 核 / 125 GiB 内存 / 2 TiB 盘，多项目混部）
- **文档日期**：2026-10-18
- **文档性质**：先行项目组在部署与侦察中发现的现存隐患汇总，供后续进场项目**避让、借鉴与自查**，非行政处置通知
- **关联文档**：《先锋项目部署规划方案v1_20261010.docx》、《15.106信息中心协调事项清单.md》§2.3

## 一、写在前面

15.106 是多项目共用主机，我方（工业图像智能体）已先行完成部署。我方全程遵循的合规基线是：

> **除平台 Web 端口（18000，按需对办公终端开放）外，数据库与工具服务一律绑定 `127.0.0.1`；不使用 Docker；不改动系统原生服务。**

在上机过程中，我们发现主机上已存在若干**非我方部署**的服务与进程，它们在网络暴露面、进程托管、端口占用和服务归属上存在不规范之处。这些问题**不会自动消失**，会直接影响后续进场项目的部署安全与稳定性。现整理通报如下，请各项目在进场前对照自查，**避免重蹈覆辙，也避免与现存隐患相互干扰**。

> 说明：以下问题均非我方部署，我方无权也不擅自处置。凡涉及清退、认领、收敛的事项，均已同步至《15.106信息中心协调事项清单.md》请信息中心拍板。本文档面向**项目团队**，重点在于"进场时你要知道什么、你要怎么做"。

## 二、现存隐患清单（问题描述 / 风险定性 / 整改建议）

| 问题描述 | 风险定性 | 整改建议 |
|---|---|---|
| **原生 MySQL（mysqld.service）`*:3306` + `*:33060` 全网卡开放** | 高：数据库端口直接暴露到园区网所有网卡，33060（X 协议）属多余暴露面；一旦弱口令或漏洞即被横向利用 | 进场项目**不得复用**此实例；各自按规划独立裸装并绑 `127.0.0.1`（我方 qc-mysqld:18020 即范例）。请信息中心推动该实例收敛绑定或关停 X 协议 |
| **Next.js 前端（next-server）`*:1015` 全网卡开放** | 高：1015 属特权端口段（<1024），进程大概率以 root 运行，既是无主暴露端口又违反最小权限 | 非本项目服务请勿改动；进场项目自研前端**一律使用规划端口段内的高位端口**并绑回环，杜绝特权端口 |
| **未知 Python 服务 `0.0.0.0:18201`** | 高：绑定全网卡且归属不明，**端口正落在数字发动机建模智能体规划段 18200–18299 内** | **数字发动机建模智能体进场前必须先 `ss -lnt` 清查 18200–18299 段占用**，撞口即报信息中心认领清退，切勿强行覆盖他人进程 |
| **PostgreSQL 17 遗留库 `hkanswer_1015 / _3014 / _alpha`** | 中：同一应用多份日期快照堆在共享实例，缺乏版本化与归档纪律，易与后来者混淆归属 | 归属"hkanswer"应用，我方及其他项目不使用；提示进场项目数据应落在**各自独立实例**，勿共享他人库 |
| **Next.js、MinerU 解析簇（40020 + 40000–40010 十余进程）非 systemd 托管** | 中高：手工拉起、无单元文件、无 Restart 策略、无资源配额，**主机重启即全部消失且不自愈** | 进场项目**所有常驻服务必须 systemd 托管**（独立账号 + 单元文件 + Restart + CPU/内存 limit），并纳入开机自启；勿效仿"游击队"式部署 |
| **firewalld 未运行** | 高：主机层无任何暴露面管控，上述全网卡绑定等同向园区网敞开，目前仅靠网络边界与各项目自律回环绑定兜底 | 进场项目**不得假设主机防火墙会替你兜底**，务必自身绑回环；同时建议共同推动信息中心启用 firewalld 或做服务级收敛 |
| **wpa_supplicant（无线协议栈）在跑** | 中：涉密/高可信环境不应存在无线栈 | 非项目可处置项，已建议信息中心禁用；进场项目勿新增任何无线/外联通道 |
| **Samba / NFS / CUPS / Exim / cockpit(:9090) / :80 socket 等默认服务未裁剪** | 中：与业务无关的系统服务构成额外攻击面（cockpit 自带 Web 管理入口） | 进场项目部署前先摸清这些既有监听，**避免与自身端口冲突**；无关服务的减法由信息中心统一处置 |
| **多个服务（18201 / 1015 / MinerU 簇）运行账号与归属不明** | 中：出问题找不到责任方，也不敢轻易处置，混部协作隐患 | 进场项目**每个服务须登记归属单位与运行账号**，写入部署台账；发现无主服务只上报、不擅动 |

## 三、给三个进场项目的部署纪律（对照规划方案）

结合上述隐患与《先锋项目部署规划方案v1》，进场前请各自落实以下六条：

1. **端口段先清查再占用**：18201 事件证明"规划段 ≠ 空闲段"。三项目进场前各自段内先 `ss -lnt` 排查，登记台账后再启动；工业图像 18000–18099、多学科仿真 18100–18199、数字发动机建模 18200–18299。
2. **回环绑定 + 例外申报**：除 Web 入口外，数据库、工具、求解器、模型服务一律绑 `127.0.0.1`；确需对外暴露的端口须书面申报并纳入防火墙策略。**坚决不接受 `0.0.0.0` 默认绑定**（部分厂商交付包默认即为 `0.0.0.0`，安装时务必改成回环）。
3. **一律 systemd 托管**：单元文件 + 独立运行账号 + Restart 策略 + 资源配额 + 开机自启，杜绝 next-server / MinerU 式手工进程，确保重启可自愈。
4. **独立环境、不碰系统 Python**：Python 基线 3.11，每个后端与每项工具各建独立 venv，用解释器绝对路径启动；venv 必须在目标机创建，不得从开发机直接拷贝。
5. **不擅动他人服务**：混部机上发现无主或异常服务，只登记、只上报信息中心，**不 kill、不改配置、不覆盖端口**，避免误伤其他项目。
6. **进场前做一次暴露面自检**：`ss -lnt` 全量核对自身监听是否都在规划段内、是否都为回环绑定（Web 入口除外），并确认没有意外拉起 Docker、无线等被禁通道。
