# 算法工具容器化离线部署指南（glibc 2.28 旁路）

> 适用范围：**交付包要求 glibc ≥ 2.28、但部署机是 glibc 2.17（NFS/CentOS 7 代基座）导致裸机装不上**的算法工具。
> 目前唯一命中此条件的是 **金相 metallography（18013）**（整栈 torch 2.14 / numpy 2.4 / opencv 5.0 均为 manylinux_2_28）。
> 其余工具（孔探/热端/荧光）能裸机装，走 [`deploy/README.md`](README.md) + `install_ai_tool.sh`，**不需要本文的容器路线**。
>
> 与平台"非容器化"决策的关系：那条决策针对**平台自身**（裸机 venv + systemd）。本文只对**单个被 glibc 卡死的算法工具**做容器旁路，平台侧仍按 §5 切端点接入，不改变平台形态。

---

## 0. 为什么要容器（一句话原理）

manylinux_2_28 的 wheel 把 `GLIBC_2.28` 的符号引用**烧进了 ELF**，运行时无法关闭；glibc 2.17 主机真没有这些符号。
原地升级主机 glibc 会变砖（禁止）。唯一安全的"旁路满足"手段就是**容器**：用一个自带 glibc 2.28 的底座镜像跑工具，主机 glibc 不参与。

> ⚠️ 区分两码事：**"装不上"（glibc 环境）** 与 **"接口不合规"（返工）** 无关。金相是前者（接口零返工、六工具里最规范）；X光是后者（等开发方改接口），跟容器无关。

## 1. 部署前判定：这个工具到底要不要容器

在目标机（glibc 2.17）上探交付包 wheel 实际引用的最高符号版本：

```bash
# 对可疑的编译 wheel 逐个扫（示例：torch/numpy/contourpy）
TMP=$(mktemp -d); W=/opt/agent/vision-agent/tools/<tool>/app/<offline>/wheels
for whl in "$W"/*manylinux*.whl; do
  unzip -oq "$whl" -d "$TMP" 2>/dev/null
  find "$TMP" -name '*.so' -exec objdump -T {} \; 2>/dev/null \
    | grep -oE '(GLIBC|GLIBCXX|CXXABI)_[0-9.]+' | sort -uV
done
rm -rf "$TMP"
```

- 出现 `GLIBC_2.28`（或更高）→ 主机 2.17 跑不了 → **走本文容器路线**。
- 只有 `GLIBC_2.17` 及以下 → 能裸机装，回 `deploy/README.md`。
- 附带看 `GLIBCXX_3.4.22` / `CXXABI_1.3.11`：主机 libstdc++ 若只到 `GLIBCXX_3.4.19`，是**双缺口**，更没救，只能容器。

## 2. 底座镜像选型（关键：OpenSSL 版本要对齐）

金相的 runtime 是 `Python-3.11.16-NFSChina4-x86_64-runtime.tar.gz`，在 **OpenSSL 1.1.1k** 上编译，`_ssl` 扩展动态链接系统 `libssl.so.1.1`。

| 候选底座 | glibc | OpenSSL | 结论 |
|---|---|---|---|
| **`debian:buster`** | **2.28** ✅ | **1.1.1** ✅ | **选它**——与验证环境（NFS V4.0 = glibc 2.28 + OpenSSL 1.1.1）精确对齐 |
| `python:3.12-slim`（bookworm） | 2.36 | 3.x ❌ | glibc 够，但 OpenSSL 3.x 会让 `import ssl` 崩（runtime 要 1.1） |

> buster 已 EOL，apt 源必须指向 `archive.debian.org` 且关 `Check-Valid-Until`（见 §4 Dockerfile）。

**内核前提**：容器跑 glibc 2.28 用户态只需内核 ≥ 3.2；本机 3.10.0-514 满足。docker 26.1.4 + overlay2 + cgroup v1 已验证可用。

### 3.2 修复 wheel 文件名被 ISO9660 截断的缺陷（金相交付包实测踩中）

**症状**：`install_offline.sh` 的 `[5/6]` 报 `No matching distribution found for contourpy==1.3.3 (from versions: none)`。
**根因**：交付方把材料烧成 ISO 镜像时，长文件名被砍到 ~64 字符，`contourpy-…manylinux_2_28` 丢了 `_x86_64.whl` 尾巴 → pip 只认 `.whl` 结尾，直接无视。文件内容完好，坏的只是名字。

```bash
cd /opt/agent/vision-agent/tools/metallography/app/<offline_dir>
# 1) 看有没有"不以 .whl 结尾"的残缺轮子（有就是中招）
ls wheels/ | grep -vE '\.whl$'
# 2) 用包内 SHA256SUMS.txt 的权威完整名，按前缀批量改回
ls wheels/ | grep -vE '\.whl$' | while IFS= read -r bad; do
  good=$(awk -v b="./wheels/$bad" 'index($2,b)==1{print $2; exit}' SHA256SUMS.txt)
  if [ -n "$good" ]; then mv -v "wheels/$bad" "${good#./}"; else echo "!! 无法匹配: $bad"; fi
done
# 3) 校验内容完好（改名没改字节，应全 OK）
grep '/wheels/' SHA256SUMS.txt | sha256sum -c - | grep -v ': OK' || echo "全部 wheel 校验通过 ✅"
# 4) 数量应与 requirements 行数一致（金相：46）
ls wheels/*.whl | wc -l
```

> 其它工具包（X光/荧光）实测文件名**未被截断**（更长的 `markupsafe-…2_17_…2_28_x86_64.whl` 都完整），无需此步。判定：`ls <pkg>/wheels/ | grep -vE '\.whl$'` 输出为空即正常。

## 4. Dockerfile

写到**离线包的父目录**（本例 `/opt/agent/vision-agent/tools/metallography/app/`，即 build 上下文根），文件名 `Dockerfile`：

```dockerfile
FROM debian:buster

# buster 已 EOL → archive 源 + 关有效期校验；补齐预编译 Python 运行所需的系统共享库
RUN echo 'deb http://archive.debian.org/debian buster main' > /etc/apt/sources.list \
 && echo 'deb http://archive.debian.org/debian-security buster/updates main' >> /etc/apt/sources.list \
 && apt-get -o Acquire::Check-Valid-Until=false update \
 && apt-get install -y --no-install-recommends \
      libgomp1 libssl1.1 libffi6 libsqlite3-0 libbz2-1.0 liblzma5 zlib1g libgfortran5 \
 && rm -rf /var/lib/apt/lists/*

# install_offline.sh 内部用了 sudo；容器内 root 无需真 sudo，做透传垫片
RUN printf '#!/bin/sh\nexec "$@"\n' > /usr/bin/sudo && chmod +x /usr/bin/sudo
ENV USER=root

# 离线交付包整体拷进容器（目录名按实际改）
COPY metallography_api_offline_20260915/ /opt/meta_offline/
WORKDIR /opt/meta_offline
RUN bash install_offline.sh

EXPOSE 18013
# ★ 启动脚本留在 /opt/meta_offline，不在 install 生成的 app/ 里；CMD 必须用绝对路径
CMD ["bash","/opt/meta_offline/start_server_metallography.sh"]
```

**apt 库清单说明**（buster 基础镜像为精简未预装，且 apt 走明文 http 时连 openssl 都不会自动拉）：

| 包 | 支撑 |
|---|---|
| `libssl1.1` | `import ssl`（runtime 的 `_ssl` 链接 `libssl.so.1.1`） |
| `libsqlite3-0` | `import sqlite3` |
| `libbz2-1.0` / `liblzma5` / `zlib1g` | `import bz2/lzma/zlib` |
| `libffi6` | `import ctypes` |
| `libgfortran5` | numpy/scipy 的 OpenBLAS |
| `libgomp1` | torch/opencv 的 OpenMP |

## 5. 构建

```bash
cd /opt/agent/vision-agent/tools/metallography/app        # build 上下文 = 含离线包 + Dockerfile 的目录
docker build -t ai-tool-metallography:latest .
```

正常应一路跑到 `OFFLINE INSTALLATION COMPLETE` + `Successfully tagged`。

### 构建期报错对症速查

| 报错 | 原因 | 处理 |
|---|---|---|
| `[2/6] ImportError: libxxx.so.N: cannot open shared object file` | 基础镜像缺该共享库 | 把对应 apt 包加进 §4 的 `apt-get install` 行，重 build（如 `libxxx.so.N` → 搜对应 `libxxx-N` 包） |
| `[5/6] No matching distribution found for <pkg> (from versions: none)` | wheel 文件名被截断（见 §3.2） | 按 SHA256SUMS 改名后重 build |
| `[6/6] import torch` 报 `libgomp.so.1 not found` | libgomp1 没装上 | 确认 apt 行含 `libgomp1` |
| pip 报某库 `.so` 缺（如 `libatomic.so.1`） | torch 等还依赖个别库 | 补 `libatomic1` 进 apt 行 |

> 诊断总原则：遇 `ImportError: xxx.so: cannot open shared object file` **直接把 `.so` 名换成 apt 包名补上**，不要想着重编 Python 或降级 wheel。

## 6. 运行 + 验证（判真伪，别只看 health 绿）

### 6.1 先停掉占端口的 mock

```bash
systemctl stop "ai-tool@metallography" 2>/dev/null || true
systemctl disable "ai-tool@metallography" 2>/dev/null || true
ss -ltnp | grep 18013 || echo "18013 已空"
```

### 6.2 起容器（**只绑 127.0.0.1，不对公网暴露**）

```bash
docker rm -f ai-tool-metallography 2>/dev/null || true
docker run -d --name ai-tool-metallography \
  --restart unless-stopped \
  -p 127.0.0.1:18013:18013 \
  ai-tool-metallography:latest
sleep 5; docker ps --filter name=metallography     # STATUS 应为 Up
```

> 若 STATUS 显示 `Restarting (127)`：CMD 用了相对名找不到脚本 → 用绝对路径覆盖：
> 末尾追加 `bash /opt/meta_offline/start_server_metallography.sh`（或按 §4 把 CMD 改绝对后重 build）。

### 6.3 健康 + 载荷指纹

```bash
curl -s http://127.0.0.1:18013/health; echo
# 期望真模型指纹（非 mock）：
# {"status":"healthy","tool_name":"metallography_microstructure_analysis",
#  "model_architecture":"unet","model_version":"v1.0","device":"cpu","model_ready":true}
```

**判真伪看指纹，不看 200**：`model_ready:true` + `model_architecture:unet` + 真实 `tool_display_name`。

### 6.4 实打一次推理（inference 必带 `task_id`）

```bash
curl -s -X POST http://127.0.0.1:18013/api/v1/inference \
  -F "task_id=manual-check-001" \
  -F "image=@/opt/agent/vision-agent/tools/metallography/app/<offline_dir>/test01.png" \
  | head -c 2000; echo
```

- 只发 `image` 会返回 `{"code":1001,"message":"missing required field(s): task_id"}`（错误码合规，补 `task_id` 即可）。
- 正常返回：顶层 `code:0` + `result.status:success` + γ′ 占比（≈0.516）+ `instances[]` 逐颗粒 + `artifacts[]`（带 `uri`）。

## 7. 接入平台（切端点，热生效）

```bash
bash /root/QualityCheckingAgent/deploy/switch_tool_endpoint.sh \
  metallography_defect_detection_v1 \
  http://127.0.0.1:18013 http://127.0.0.1:18013/health

```

- **meta_json 注意**：`switch_tool_endpoint.sh` 第 4 个参数会**整体覆盖** `meta_json`。若现有金相能力的输入契约（`input_required=image` 等）要保留，**不要传 `'{}'`**，就只给前 3 个参数；确需给真实契约时才传第 4 参（JSON 内只允许双引号）。
- 已知正常现象：脚本第 3/4 步 `POST /capabilities/reload` 返回 401（AuthMiddleware）、第 4/4 步可能 JSONDecodeError——只要第 2 步回读看到 `version+1` 且新端点 `/health` OK，即已落库生效。
- 平台侧归一器 `transform_metallography` 已就绪（把 γ′ 定量结果归一为"分析上报"结论，不伪造严重度），**无需改代码**。

## 8. 持久化 / 开机自启

容器用 `--restart unless-stopped` 已能在容器异常和 docker 重启后自恢复，但**宿主机重启**需保证 docker 守护进程自启：

```bash
systemctl enable docker
```

如需与裸机工具统一的 systemd 管理，可加一个 `ai-tool-metallography.service` 单元 `ExecStart=/usr/bin/docker start -a ai-tool-metallography`（可选，非必需）。

## 9. 纯内网（无外网）导入 checklist

内网机器拉不到 `debian:buster`、也连不上 archive 源时，在**有网机器**预先把镜像导出：

```bash
# 有网机器：build 完（或 docker pull debian:buster 后 build）
docker save -o ai-tool-metallography.tar ai-tool-metallography:latest
# 连同交付包一起拷进内网（U 盘/内网传输）
```

```bash
# 内网机器：加载镜像，直接 run（§6.2），无需 build、无需外网
docker load -i ai-tool-metallography.tar
```

> 若内网要从源码重建：需同时带入 `debian:buster` 基础镜像 tar + 离线交付包，且 build 时 apt 仍要能拿到 §4 那批 `.so` 包（离线场景需自备 buster 的 deb 或改用已含这些库的底座）。**推荐"有网 build → docker save → 内网 load"** 这条最省事。

需要拷贝进内网的产物：
1. `ai-tool-metallography.tar`（已 build 好的镜像）
2. 金相交付包（含已改名的 `wheels/`，用于 `test01.png` 与备查）
3. `deploy/switch_tool_endpoint.sh`（平台侧切端点，随 quality-agent 源码已在内网）

## 附录 B：本次踩坑复盘（供同类工具速查）

1. **glibc 不是靠猜**：`objdump -T` 探最高符号版本 + `pip debug --verbose` 看兼容标签，一次定位（金相 buster 上 pip 头名即 `manylinux_2_28`，证明 glibc 已不是障碍）。
2. **缺 `.so` 打地鼠要一次配齐**：预编译 Python 动态链接系统库，buster 精简镜像没预装；`libssl1.1/libsqlite3-0/libbz2-1.0/liblzma5/zlib1g/libgfortran5` 一把加全。
3. **`from versions: none` ≠ 平台不符**：先 `ls wheels/ | grep -vE '\.whl$'` 查文件名是否被 ISO 截断，用 SHA256SUMS.txt 改名。
4. **容器 Restarting(127)** = 命令/文件找不到：CMD 相对名 vs WORKDIR 不匹配，用绝对路径。
5. **`/health` 200 不代表真模型**：必须核 `model_ready:true` + 架构/版本指纹 + 实打 inference 看 γ′ 载荷。
